# Repository instructions

## Code maintenance

- Add concise comments to changed code when they help explain the intent or a non-obvious decision.
- When a bug is discovered, add its case as a regression test and verify that the test passes after the fix.

## Verification

- Before creating a release, run the full test suite and stop the release if any test fails.

## Git commits

- When commits are requested, split changes into logical feature-focused commits and use messages that clearly describe each change.

## Release notes

- A release request includes writing and verifying Korean release notes after the existing release workflow succeeds. Confirm the actual published release and tag before editing its body.
- When asked to backfill notes, process only the requested releases with empty bodies or autogenerated changelog links only. Preserve manually written descriptions; do not rebuild releases or change tags or assets.
- Identify the previous published release appropriate to the target's release line and prerelease status, and verify its tag is a valid comparison base. Do not choose a base solely by date or tag sorting. Report ambiguous or missing comparison refs instead of guessing.
- Read commit subjects and bodies between the tags and inspect the final diff between the two release snapshots. Consult code and tests at those versions when needed; do not describe later changes. For the first release, summarize the features present at its tag.
- Write concise, accessible Korean notes highlighting the main changes and their user-visible effects. Group related commits by behavior; use feature, bug-fix, and maintenance sections only when useful, and include a full comparison link when a previous release exists.
- Refer to the app's todo items as "일정", not "할 일", in Korean release notes.
- Exclude reverted changes and automatic version-bump commits. Keep internal maintenance brief and do not claim benefits, performance gains, or behavior unsupported by the code.
- Update the GitHub release body directly using available GitHub authentication. The issue-bot requirement below applies to issue operations, not release notes. Use temporary files outside the repository if needed; never commit release-note files.
- Re-read the current body before updating to preserve existing manual content, then fetch the published body to verify the result. If updating fails, retry only the body update and report incomplete releases; do not recreate the release.
- Editing existing release notes alone does not require rerunning application tests. Creating a release still requires the full test suite described above.

## GitHub issue operations

- Do not comment on, close, or reopen issues directly with the repository owner's `gh` credentials.
- Dispatch `.github/workflows/issue-bot.yml` so issue activity is attributed to `github-actions[bot]`.
- Wait for the workflow run to succeed, then verify the issue state or comment author.
- Write concise Korean comments that match the repository owner's usual tone.
